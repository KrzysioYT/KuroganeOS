# KuroganeOS repository audit — 2026-08-18

Audit target: KuroganeOS 3.3.3-dev / DEV BETA.

This document records repository, boot-media, networking, documentation and
qualification findings discovered while investigating Windows VirtualBox
`No bootable drive` reports and network-driver portability.

## Executive summary

The repository has a strong UEFI/QEMU qualification foundation, but several
areas were out of sync with the actual source tree:

1. KuroganeOS optical media is intentionally UEFI-only. A VirtualBox VM left on
   its default legacy BIOS firmware cannot boot the ISO.
2. The repository already contains a substantial VirtIO-net PCI backend and
   the physical network selector tries it before E1000 and PCnet, while the
   roadmap and networking documentation still described VirtIO-net as TODO.
3. CI qualified E1000 and PCnet networking but did not exercise VirtIO-net.
4. CI's `make test` path ran a smaller regression suite than the older/full
   `scripts/test.sh`, leaving many existing host tests outside the merge gate.
5. Multiple current-looking documentation paths still contained 2.0 or
   3.3.1-dev statements that contradict 3.3.3-dev source and canonical docs.
6. `/state/` is ignored as generated runtime/build state, but older state/log
   files are still tracked in Git.

The audit changes on the current branch add a VirtualBox boot-repair helper,
selectable VirtualBox NIC profiles, VirtIO QEMU runtime qualification, the full
host regression suite in CI, and documentation cleanup.

## Severity A — boot/release blockers

### A1. VirtualBox default BIOS vs KuroganeOS UEFI-only ISO

KuroganeOS `build-installer-iso.sh` publishes a pure x86-64 UEFI optical image:

- El Torito platform EFI;
- no-emulation `efiboot.img`;
- GPT EFI System Partition;
- `EFI/BOOT/BOOTX64.EFI`.

There is no legacy BIOS boot loader in the ISO. This is intentional and should
remain explicit. A VirtualBox VM configured with BIOS therefore has no valid
boot path and may report `No bootable medium` / `No bootable drive`.

Mitigation in this branch:

- reference VM helpers always set `efi64` and DVD-first boot;
- `scripts/repair-virtualbox-boot.ps1` repairs an existing Windows-host VM and
  optionally reattaches the ISO;
- current VirtualBox docs make UEFI-only behavior a first-class requirement.

A future BIOS compatibility path would require a real legacy boot loader or a
separate compatibility medium. It must not be simulated by documentation or by
renaming the UEFI ISO.

### A2. Real VirtualBox smoke remains host-specific

The repository can verify El Torito/FAT/GPT/PE structure and boot the ISO under
OVMF/QEMU in CI. `verify-virtualbox-iso.sh --virtualbox-smoke` can additionally
boot Oracle VirtualBox when `VBoxManage` is installed on an x86-64 host.

Until a Windows/x86-64 VirtualBox run is recorded for a release candidate,
VirtualBox runtime status remains a host-specific qualification item rather
than an unconditional PASS claim.

## Severity B — networking

### B1. VirtIO-net implementation existed but was not qualified

`kernel/net/virtio_net.cpp` already implements a PCI VirtIO network backend:

- vendor `0x1AF4`;
- transitional network device `0x1000`;
- modern network device `0x1041`;
- modern PCI capability discovery;
- common/notify/device configuration mappings;
- split virtqueues;
- DMA-backed RX/TX buffers;
- VirtIO 1 feature negotiation;
- MAC feature support and fallback MAC.

`kernel/net/physical.cpp` probes backends in this order:

1. VirtIO-net;
2. E1000;
3. AMD PCnet.

This contradicted `docs/ROADMAP.md`, which still described VirtIO-net as an
unimplemented future backend.

Mitigation in this branch:

- QEMU smoke accepts `--nic virtio` and maps it to `virtio-net-pci`;
- CI adds a required DHCP/gateway runtime qualification for VirtIO-net;
- VirtualBox VM helpers accept `e1000`, `virtio` and `pcnet` profiles.

E1000 remains the default VirtualBox compatibility profile until a real
VirtualBox VirtIO smoke is recorded. VirtIO is the preferred portability and
performance direction for virtualized environments once both QEMU and
VirtualBox qualification are green.

### B2. Driver coverage for physical PCs is still narrow

Virtual NIC support does not replace real-hardware NIC enablement. The project
still needs common physical PCI/PCIe drivers, with Realtek and newer Intel
families as practical candidates after virtual-network stability.

Do not describe E1000, PCnet or VirtIO-net as a universal hardware driver.

### B3. Network API remains incomplete for browser-class workloads

Even with a working NIC backend, browser-grade networking still needs:

- non-blocking/async socket handles;
- event/wait integration;
- stronger TCP retransmission/order/window handling;
- public async DNS service;
- fully qualified TLS/HTTPS runtime path;
- trust-store lifecycle and update policy.

The source contains more TLS foundation than older roadmap text stated, but
runtime HTTPS should stay marked partial until a real handshake/request smoke
is part of qualification.

## Severity B — CI and tests

### B4. Existing full host tests were outside the main gate

`make test` invokes `scripts/run-host-tests.sh`, which covers SDK ABI, graphics,
VFS process paths, IPC/shared memory/events, TLS compile probe and SDK project
generation.

The repository also contains `scripts/test.sh`, which covers substantially more
existing code, including:

- allocator/libk;
- driver core and ACPI;
- installer package/disk layout;
- input/USB/user console/window manager;
- virtual memory/ELF/GPT/partitioning/AHCI;
- RAMFS/VFS/FAT32;
- scheduler/thread/process;
- network core and network protocol serialization/parsing;
- profiler and SDK tests.

This branch adds the full suite as a separate CI gate instead of silently
assuming `make test` covers it.

## Severity C — documentation drift

### C1. Current docs still referenced 3.3.1-dev

Current project version is 3.3.3-dev, but active guides still referenced
3.3.1-dev in filenames/examples/headings, including:

- `docs/START_HERE.md`;
- `docs/VIRTUALBOX.md`;
- `docs/INSTALLATION.md`;
- `docs/NETWORKING.md`;
- `docs/BUILD_STATUS.md`;
- `docs/LINUX_DEVELOPMENT.md`;
- `docs/MACOS_DEVELOPMENT.md`;
- `docs/DEVELOPERS/APP_DEVELOPMENT.md`;
- VirtualBox VM helper default names.

Active guides should prefer `3.3.x` where instructions are branch-stable and
use the actual `common/version.h` value only where an exact artifact name is
required. Release notes under `docs/releases/` are historical and should retain
their original version numbers.

### C2. Legacy duplicate docs contradict canonical docs

Examples:

- `docs/installation/VIRTUALBOX.md` said no VirtualBox-compatible NIC exists and
  installation is unimplemented;
- `docs/limitations.md` described KuroganeOS 2.0 and omitted later IPC, audio,
  filesystem and networking work;
- `docs/build.md` still centered a 2.0-era validation flow.

These paths should not remain independent sources of truth. They should either
redirect to canonical current documents or be moved into explicit historical
release documentation.

Recommended source-of-truth hierarchy:

- user start: `README.md` -> `docs/START_HERE.md`;
- VirtualBox: `docs/VIRTUALBOX.md`;
- installation: `docs/INSTALLATION.md`;
- networking: `docs/NETWORKING.md`;
- build: `docs/BUILDING.md` + `docs/BUILD_STATUS.md`;
- current limitations: `docs/CURRENT_LIMITATIONS.md`;
- active work: `docs/ROADMAP.md`;
- historical behavior: `docs/releases/*` only.

### C3. Release notes can conflict with live roadmap

`docs/releases/3.3.3-dev.md` contained statements such as desktop pin persistence
not being claimed, while the active roadmap describes `/home/desktop.cfg`
persistence as implemented. Release notes should describe the exact revision
they were written for, or be amended before 3.3.3-dev is treated as a coherent
release candidate.

## Severity C — repository hygiene

### C4. Generated `/state/` is ignored but still tracked

`.gitignore` excludes `/state/`, yet tracked repository content still includes
build locks, an image entry and historical run logs. Git ignore rules do not
remove files already tracked.

Recommended cleanup:

1. remove tracked generated `state/**` content from the index/repository;
2. keep `/state/` ignored;
3. store intentionally preserved qualification evidence as CI artifacts or
   under a clearly named immutable documentation/evidence directory rather than
   as live runtime state.

This audit records the issue but does not bulk-delete historical logs without a
separate retention decision.

## Active TODO snapshot

Highest-value remaining work after the boot/network qualification fixes:

1. real Windows/x86-64 VirtualBox ISO smoke and install/reboot smoke;
2. real VirtualBox VirtIO-net NAT DHCP/gateway/DNS smoke;
3. async socket/event API and stronger TCP;
4. qualified HTTPS/TLS request path;
5. public multi-thread/process synchronization primitives;
6. demand paging, COW, file-backed mmap and later SMP;
7. NVMe, Intel HDA and broader physical NIC coverage;
8. xHCI/USB HID stabilization across more machines;
9. settings/profile service and account/credential hardening;
10. native graphics resource/surface/present model before claiming Direct3D
    compatibility beyond the current software foundation.

## Qualification rule

A feature is considered complete only when source, public API where applicable,
documentation and an appropriate test agree. For VM hardware backends, a host
unit test alone is insufficient: the relevant emulated device must complete a
runtime smoke through the actual network/storage/audio path.
